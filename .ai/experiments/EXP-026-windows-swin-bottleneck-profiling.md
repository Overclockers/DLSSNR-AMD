# EXP-026：大型 Swin 的队列计时、硬件计数器与局部循环原型

日期：2026-10-07。状态：**定位有效；局部原型未保留；没有新的生产提速结论**。
这是用户确认后的定向研究，不是恢复此前已经结束的 `nr-optimize` 额度。

## 结论

优先研究 **C256 下采样的取指与代码生成**，降低纯队列领取优化的优先级。
此前只有约 219 KiB 的静态机器码证据；本轮三次硬件捕获中，该内核的指令缓存命中率
稳定在 **44.39%～44.80%**，另外五个 persistent 内核为 64.21%～76.93%。
低命中率是值得干预的信号，尚不能证明取指停顿主导全部耗时。

稀疏队列计时中，领取任务占工作组记录寿命的 **1.21%～3.38%**，
计算主体、参数准备及末端 release/join 占 **90.80%～97.31%**。
这不支持“主要时间花在等待 ready queue”的假设，也不是可直接相加到整帧的提速上限。

据此验证了一项最小代码生成原型：只把 C256 DS 的成对 MLP contract K 循环改为每次展开四段。
FP32 输出一致、没有 scratch，但机器码从 224,384 增至 225,408 字节，未达到缩小代码目标。
没有将其提升到生产源或宿主，也没有按单次筛选时间宣称性能通过。

## 队列观测：补齐之前没有测到的区间

现有 `NR_PROF_ITEM_START` 位于领取之后，`ITEM_WAITED` 不覆盖生产 DF=1 路径。
私有原型在 `fswin_t.comp` 加入四个时间点：领取前、领取及广播后、body 的 release/barrier 后、
消费者发布后；另外记录工作组开始/结束、退出领取、epoch、item、layer 和 live mask。

每个被采样工作组仅 lane 0 写自己的固定记录区，不通过全局原子分配日志槽，也不增加 barrier。
采样选择为 `wg_id % 8 == epoch % 8`，五次采集改变末帧 epoch；另做一次全工作组采集。
这仍会影响代码生成、寄存器和调度，不能称作零开销。

| 内核 | 领取占比，五次范围 | body/准备/release 占比，五次范围 | 全量任务数 |
| --- | ---: | ---: | ---: |
| C64 DS | 2.53%～2.59% | 94.50%～94.69% | 12,069 |
| C128 DS | 3.17%～3.38% | 90.80%～91.53% | 4,613 |
| C256 DS | 1.41%～1.44% | 96.39%～96.49% | 1,596 |
| C256 UPS | 1.21%～1.24% | 97.20%～97.31% | 1,596 |
| C128 UPS | 2.03%～2.09% | 95.63%～95.78% | 4,612 |
| C64 UPS | 2.89%～2.97% | 93.97%～94.08% | 12,069 |

分母是采样工作组的寿命之和，有并发重叠。body 包含同步及其等待，不代表纯 ALU 执行时间。
退出领取最多约 0.132%；未分类的循环同步、记录及首尾间隙约 0.586%～0.962%。
C128 DS 的发布区间约 4.26%～5.17%，值得保留为次要观察点。

全量记录的 **36,555 个 item 各出现一次**；epoch、时间顺序、记录容量及错误字检查通过。
禁用诊断时，重编译六个内核的 SPIR-V 与各自独立基线逐字节一致。
开启诊断后，VGPR/SGPR 会变化，例如 C256 DS 的 VGPR 229→224；六个内核均无 scratch。
因此这些占比用于筛选方向，不能当成未插桩原路径的精确成本分解。

另一个线索：全量记录中，把 C64 DS 限定在同一层（layer=1）、完整窗口（mask=15），
工作组 0～63 的 body 中位数为 14.52 μs，448～511 为 47.18 μs（各 501 / 170 个任务）。
它说明存在明显执行不均，与历史 wave 年龄现象相符；工作组 ID 本身不能证明 CU 的实际驻留顺序。
还没有从 SQTT 解码出对应的 wave 占用或指令时延，不能把这个差异全归因于 oldest-first。

## 硬件计数器：对齐到实际 dispatch

共四份 RGP：一份原普通 benchmark 的详细跟踪；一份带逐层时间戳的详细跟踪；
两份关闭详细指令跟踪、保留计数器的重复捕获。全部使用未改的基线着色器。
后三份均与导出的 Vulkan 绝对时间戳精确对齐到第 99 帧的全部 123 个 dispatch。

采样周期为 4096 GPU cycles；时间基准由 RDP SystemInfo 确认为 100 MHz，
与 Vulkan `timestampPeriod=10 ns` 一致。只纳入整个采样区间都落在该 dispatch 内的样本。
命中率用 hits/requests 汇总，不能对每个时间点的百分比直接求平均。

| 内核 | 指令缓存命中率 | L0 命中率 | L2 命中率 | LDS bank conflict 指标 |
| --- | ---: | ---: | ---: | ---: |
| C64 DS | 76.82%～76.93% | 70.86%～71.03% | 94.86%～94.89% | 0.00% |
| C128 DS | 64.21%～64.75% | 48.58%～48.72% | 97.97% | 0.021%～0.027% |
| C256 DS | **44.39%～44.80%** | 32.74% | 98.83% | 1.36%～1.38% |
| C256 UPS | 72.70%～73.61% | 33.52%～33.65% | 98.84% | 2.60%～2.64% |
| C128 UPS | 75.81%～76.05% | 54.07%～54.23% | 97.72%～97.74% | 0.00% |
| C64 UPS | 76.16%～76.35% | 72.03%～72.24% | 94.69%～94.72% | 0.010%～0.026% |

关闭详细指令跟踪的两次 C256 DS 命中率为 44.39% / 44.48%，没有因关闭跟踪而消失。
C256 UPS 同样有超过 200 KiB 的机器码，却有明显更高的指令命中率；
**静态总大小不足以判断动态代码工作集**，下一步应定位执行最频繁的 body 和指令区间。

Memory unit busy 约 92.6%～99.7%，Memory unit stalled 约 13.5%～18.7%；
它们涵盖缓存层次与请求停顿，不能等同“显存带宽已满”。本轮不从这些值估计可节省毫秒数。
采集器给出的 LDS 指标整体较低，进一步无依据修改所有 LDS 布局的优先级也应下降。

RDF 容器按 AMD 公开格式解析；31 个 `DerivedSpmCtr` 的内部布局由长度、内嵌名称/描述及
子计数器关系推导，并逐样本验证八组比率，以及 instruction requests = hits + misses。
三份对齐捕获分别有 12,521 / 7,160 / 7,241 个样本，全部验证通过。
这是本地读取工具写出的派生计数器；没有声称完成 SQTT 的指令时延分析，也没有把 GUI 截图当输入。

## 由证据驱动的单项原型

`fswin_body.glsl` 的成对 contract K 循环只用 K 索引 LDS 和权重；其 private 数组仍按常量 m 索引。
因此选它做每次四段的局部循环，保留 K 的 0、1、2……累加顺序，以及全部五种边缘 body。
这是一个机制、一版原型，没有全局关闭 unroller，也没有重复修改 EXP-020 的扩张分工。

| 指标 | 基线 | 原型 |
| --- | ---: | ---: |
| 驱动 ELF `.text` 字节 | 224,384 | 225,408 |
| 静态 ISA 指令行 | 31,956 | 32,344 |
| 静态 WMMA 指令行 | 4,138 | 3,850 |
| VGPR | 229 | 233 |
| scratch 字节 | 0 | 0 |

SPIR-V 多出五个 `DontUnroll` 循环，ISA 也有相应回跳；不能解释成“驱动完全忽略循环控制”。
虽然静态 WMMA 行减少，其他生成代码的增加抵消了缩减，最终 `.text` 增加 1,024 字节。
这是本原型未继续提升的原因，尚未逐条定位新增指令的来源。
原型补丁 SHA-256：`2837f3effd3f4dc8dc1be12eb9f542d22b673a6ab0adbae9a1cce03adf91c3fb`。

原型做了 pipeline-stats 验证及一次普通 standalone 筛选，FP32 输出均一致。
筛选末帧 C256 DS 为 724.9 μs；这是单帧诊断，**不是重复 A/B 的性能验收**。
既然未通过代码体积这一机制门槛，没有扩大到完整宿主对照、时序/边界验收或集成。

## 计时与验证边界

本轮 18 次 GPU 程序调用的 18 份静态 FP32 回读全部与独立基线逐字节一致；
这支持诊断样本和该原型的静态正确性，不替代全模型中间值、边界、history 或真实运动验收。

普通队列诊断各预热 100 帧、测量 200 帧（五次稀疏采集为 200～204），然后单独清空日志并采集一帧。
stats 构建仅预热 3 / 测量 3 帧，只用于代码与资源查询。
首次硬件捕获预热 100 / 测量 500；其余三次为 100 / 200，捕获发生在预热末帧。

特别注意现有 runner：`NR_PROF` 的最后一次采集会覆盖 `runner.step_ms`，所以随后打印的
逐内核表属于该**采集末帧**；之前 `GPU total ... over N frames` 的总数仍属于重复测量区间。
本轮汇总已显式标注这个区别，不把逐层末帧表当作 200 帧均值。
没有报告新的完整宿主收益；没有修改 Linux、生产 shader、外部宿主、部署或发布配置。
没有创建提交或推送，原有 `.codegraph/` 未触碰。
