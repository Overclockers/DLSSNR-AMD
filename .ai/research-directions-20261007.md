## 判断

**还有研究空间，下一步应优先查大型 Swin 内核的指令供给、任务调度和最后的图像中转。**
EXP-016..025 否定了若干具体的分工、预取和 LDS 变体，没有证明硬件或无损性能已经到顶。
不过，没有新的瓶颈证据就重复扫 wave、KFRAG、LDS 参数，预期价值已经很低。

保留结果也有共同点：EXP-001/002 针对实际边缘或矩阵形状；EXP-007/009/011/012
消除明确的整图重复工作；EXP-013 消除工作组内部不必要的全局原子通信。
下一项候选应同样指出实际消除的工作，并计算其适用范围。

## 先补充观测：决定下一次实验测什么

历史反复出现“VGPR/静态指令减少，但完整路径不快”，而频率、温度、硬件停顿和流量尚未持续采集。
应先对普通离线网络捕获指令时延、wave 占用、指令缓存、L0/L2、LDS 冲突和实际显存读写，
再选下面的一个机制。配对时间继续用独立的低插桩完整宿主路径；采集器中的时间用于归因。

AMD 官方资料确认 RGP 支持 Windows、RX 9000、Vulkan/D3D12，支持无 Present 的纯计算捕获；
其文档列出了指令缓存命中、LDS 冲突和显存流量等观测。当前机器是否已装工具、驱动是否能
成功捕获仍未验证。RDNA4 的 RGP 不显示 L1 cache counter，不能照搬旧架构的检查清单。
详细指令采集会扰动性能，不能拿它替代 production A/B。
参见 [支持范围](https://gpuopen.com/manuals/rgp_manual/)、
[纯计算支持](https://github.com/GPUOpen-Tools/radeon_gpu_profiler/releases/tag/v2.4)、
[计数器与指令时延](https://gpuopen.com/manuals/rgp_manual/events_windows/)、
[捕获选项](https://gpuopen.com/manuals/rdp_manual/features/)。

另一个具体工具缺口：`fswin_t.comp` 的 `NR_PROF_ITEM_START()` 在任务领取之后；
`NR_PROF_ITEM_WAITED()` 在 `NR_PERSIST_DF == 0` 分支，而生产配置为 DF=1。
因此直接打开现有宏，不能得到当前 ready queue 的领取/等待成本。
需在 claim 前后增加稀疏记录，并分别记录 body、发布消费者和队列空等，避免全量原子日志改变调度。
已有 `NR_PROF_STAGES` 可帮助分解 body，但不能补上缺失的领取区间。

## 方向 A：大型内核的代码体积与指令缓存（优先调查）

这是本次新增的静态证据：解析 gemm9070xt 保存的驱动 ELF，读取真正的 `.text` 段，
而非用 SPIR-V 文件大小或反汇编文本字节数代替机器码。

| 内核 | `.text` 字节 | KiB |
| --- | ---: | ---: |
| `fswin32` | 38144 | 37.25 |
| `fswinimagepreds32` | 25856 | 25.25 |
| `fswinimagepost32` | 24576 | 24.00 |
| `fswinpds64` | 56960 | 55.625 |
| `fswinpds128` | 65408 | 63.875 |
| `fswinpds256` | 224384 | 219.125 |
| `fswinpup256` | 213120 | 208.125 |

C256 DS/UPS 对应旧 ISA 分别约 31956/28897 条静态指令行；这不是每个窗口实际执行的指令数。
启用边缘 body 时，源码把 `fswin_body.glsl` 按 15/12/3/10/5 五种 mask 实例化，Windows 构建还会展开循环。
两者给出了检查代码工作集的理由，**尚不能证明 instruction-cache miss 是瓶颈**。
宿主与主仓配方有既有差异：当前宿主仅在上述 C256 DS/UPS 启用这些边缘 body，
C32、C64/C128 DS/UPS 仍关闭；表中只代表已保存的宿主诊断产物。

最小推进方式：先关联 C256 执行区间的指令缓存与指令时延，再挑一个不依赖动态 private-array
索引的循环，研究有限展开或公共代码生成方式；保留每条数值链的顺序。
不能从主仓配置推断宿主的 C32 已有五份 body，再声称删掉它们会省代码。
也不要直接拆开依赖队列中的 C256 内部/边缘任务，那会改变生产者就绪与执行契约。

与旧实验区别：EXP-001 已证明特定边缘 body 值得保留，这里研究保留边缘收益时的代码工作集；
不把关闭边缘优化或全局关闭 unroller 当成新方案。`unroll_glsl.py` 明确解释了动态索引落入
scratch 的历史原因。没有取指瓶颈、重新出现 spill，或 body 变小却完整路径变慢，都应停止。

## 方向 B：persistent 任务的空间顺序与队列等待（观测后推进）

六个内核合计 3.8149 ms，是最大的共同研究对象。当前 `nr_graph.cpp` 按递增 item ID
生成无依赖的 `init` 表；后续消费者在最后一个生产者完成时进入 ready queue。
跨组激活仍经过全局内存，队列和 epoch/依赖计数保证就绪。

最小新机制是：只重排初始可执行任务的空间顺序，保持 item 身份、依赖图、每个输出的运算
顺序和发布协议不变，研究相邻窗口的缓存访问以及后继解锁时机。先比较一项明确的局部块排序
与原行优先顺序；不并行改队列、分块和权重布局。若观测显示主要问题是 claim/publish 等待，
再研究就绪发布，而不是预先假定全局内存带宽已满。

与旧实验区别：EXP-005 调整的是 dispatch barrier/arena；EXP-013 是组内广播；
EXP-014 是领取后的层号查询。它们不直接验证本方向。源码已有 straggler queue、单 item
工作组和 PBATCH 机制；简单重新启用这些现有开关不计作新机制，C128 去除 straggler
也已经在 EXP-002 试过。

门槛：稀疏时间线应先显示等待、访问距离或尾部不均；任务重排后检查每个 item 恰好一次、
epoch、越界和错误字，再做逐层输出及完整路径对照。缓存命中改善也不能单独当作性能通过。

## 方向 C：最后的 post 与颜色合成融合（最具体的新实现候选）

当前目标路径仍是 `fswinimagepost32` 写 `s.surf0`，随后 `runtime_transfer.comp`
读取这个 FP32 model 图像并合成到 packed 输出。`model_pair()` 在整数尺寸相等时只读本像素，
因此单遍同尺寸下，可以研究在 post 的逐像素结尾完成相同合成并直接写目标 packed 图像。

这与 EXP-012 不同：它消除了合成结果的 FP32 写回和后续 blit；本方向试图消除的是
**合成之前的 model 图像写入/读取**。也与 EXP-015 删除合成分支不同。
2258×1270 RGBA32F 的一次完整写入加读取是 91,765,120 字节，约 91.8 MB 逻辑流量；
实际显存流量可能因缓存不同，不能用这个数字直接推导节省时间。
当前合成段约 0.133 ms，但融合后仍要执行合成数学，不能把整个合成段算作收益。

首个原型只覆盖线性 R11G11B10、100% 尺度、单遍、无预处理/外部 mask 的已支持入口，
其余走既有路径。沿用独立 descriptor/recording 生命周期；原图同像素采样必须先于原地写入，
不得让其它 invocation 读到已改写邻域。保留全部 FP32 表达式、舍入、饱和与 packed 转换。
融合可能让编译器跨旧 image-store 边界改变 FMA/舍入，需要中间值探针证明，而非仅看照片。

预期代价是 post 的 VGPR、代码和存活期增长；EXP-006 已提醒融合可能更慢，但其八组 FFWD
跨 wave 交换与本次逐像素 epilogue 不同。若性能通过，再扩大控制、HDR、奇数边界、回退和
历史验证。历史必须仍保存合成前的 network 输出；不允许把最终 packed 图像当作历史。
`NR_POST_NO_OUT1=1` 已去除无历史时的冗余第二输出，这项不能重复当作新收益。

## 方向 D：带运动与历史的离线基准（补齐研究范围）

当前主要性能样本无 history；已有小尺寸宿主 fixture 验证过历史顺序和生命周期，
却不能说明目标尺寸 temporal pre/post、深度选择和历史重采样的性能分布。
可在离线 harness 加入确定性的运动纹理、深度、平移/遮挡/切镜序列，并独立记录首次帧、
稳定历史帧、reset、DRS 和控制变化。它不需要恢复游戏测量。

这条线先产出性能与正确性基线，不能预报提速。若历史采样/历史存储成为新增热点，
再研究其同精度数据布局与调度；不能用无历史照片的一致性替代时序验收。

## 可选有损路线：自适应 ViT 复用

此前 [参考项目审阅](reference-porting-review.md) 提到跨帧复用，EXP-001..025 尚未给出
当前目标链路的实现与测量。如果用户要探索更大的性能/画质取舍，可在离线运动基线建立后，
优先研究只缓存全局 ViT 分支、其余编码/解码按帧计算；先由实际图依赖明确缓存边界。

当前全部 ViT 诊断合计只有约 1.556 ms，占算子约 15%；理想化每隔一帧省去整段，
平均最多减少该诊断中的约 0.778 ms 毛工作量，且还未扣除判定、缓存与强制刷新成本。
这是范围估算，不是实测收益，也不保证八组 ViT 都能被这样的缓存边界跳过。
运动少不代表输入相同，曝光、噪声、历史和控制变化均可能影响结果；不能称作无损。

依 [decisions.md](decisions.md)，它必须独立开关、默认关闭，关闭恢复完整路径；
最终交付需菜单与 INI，并覆盖运动、遮挡、切镜、曝光、尺寸/控制变化和开→关恢复。
跳块、低精度与更小模型分辨率另行评估，不能捆绑成一个不可拆分的“快速模式”。

## 暂不投入与建议顺序

- 不再无依据重扫 EXP-003/004/016..025 的 wave、量化、预取与 LDS 参数；更少 VGPR 不是验收指标。
- 跨 API 零拷贝后置：当前四段实际搬运合计约 0.092 ms，整个非算子区间约占 3.9%；
  这只限定当前离线基线，不代表其它负载永远如此。新共享图像契约的工作量目前不划算。
- 不直接缩减 2368×1280 工作尺寸或裁掉 padding：窗口、shift、ViT keys 和位置关系可能改变结果。
- 不整体重写 HIP/D3D12 后端来赌编译器；若新指令证据支持某个 codegen 问题，先做单算子验证。

**建议下一步先完成一次大型 Swin 的瓶颈采集，然后在 A/B 中选择有证据的一项；
若要直接选择一个尚未做过的实现原型，优先 C（post→compose 融合）。**
D 可作为后续无损与有损研究共同的验证基础。各项一次只改一个机制，保留独立基线，
完整宿主交错/反序对照和同路径控制通过后才扩大集成；不能仅凭局部最快值保留。
